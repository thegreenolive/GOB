# 04.03 The Essential Model

This model describes exactly _what_ tasks (modules) are necessary to solve the problem. The main tool used at this level is the **Hierarchy Chart**. The Hierarchy Chart is a graphic tool that prioritizes modularity and top-down decomposition.&#x20;

There are three elements of hierarchy charts that serve as guidelines for maintaining consistency and clarity: notation (visual elements), structural logic, and module definitions.&#x20;

* **Symbols**: Only two graphic symbols are used: rectangles (to represent modules) and connecting lines (to show relationships)
* **Top Level**: The highest level of the chart consists of a single rectangle, representing the entire problem under consideration.
* **Decomposition**: A vertical line under a rectangle indicates that the module is being decomposed into smaller sub-problems.
* **Minimum Modules**: A decomposition must consist of at least two modules; otherwise, it is not a true decomposition.
* **Module Naming**: Text inside a rectangle may be a module name, a phrase indicating the purpose, or a collection of instructions.

Problem 1 could serve as an example for creating an essential model. Chapter 03 identifies 3 big steps to solve the problem:

1. Initialize the variables.
2. Get input, sum it, and check whether the next one is needed.
3. Report output.

These three tasks are by themselves modules used to solve the problem. The hierarchy chart in Figure 04.03 is obtained by using this general description of the solution.

It is important to note that the Hierarchy Chart does not include any element to indicate iteration or the decision to finish it. This omission aligns with the guidelines above on Hierarchy Charts.

As with walkthroughs, essential models can be refined to add more information and details. As previous analysis of the problem shows, at least three variables are needed:&#x20;

1. NUM: the input
2. SUM: the result of the addition
3. COUNT: the number of inputs entered so far

Therefore, a more detailed essential model can be constructed to include that information. &#x20;

The plasticity of the essential model allows it to be redesigned at any time to incorporate new information about the problem and allocate the corresponding tasks. For example, if the user simply states that the program will receive only integers, a new task "**Validate NUM**" needs to be added under **Process NUM,** just to the right of **Input NUM**.

***

The essential model provides little information about the decisions involved in solving the problem. In the Problem 1 example, there is no specification of when to stop receiving numbers or how to achieve it.
